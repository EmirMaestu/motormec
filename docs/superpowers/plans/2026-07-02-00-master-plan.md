# Momec — Plan Maestro de Implementación (post-auditoría)

> **Para el que ejecuta (humano junior o LLM):** este es el ÍNDICE. No implementes desde
> acá. Cada fila apunta a un archivo de plan detallado, task por task, con código completo,
> tests y comandos. Ejecutá los planes **en orden de fase** (0 → 6). Dentro de cada plan,
> ejecutá las tareas en orden. Los pasos usan checkboxes `- [ ]` para ir tildando.

**Objetivo:** llevar Momec de "MVP técnico bueno" a "producto listo para producción y
para cobrar", corrigiendo primero los bugs que corrompen datos, después endureciendo
seguridad, después completando el negocio (cobro/factura) y la UX, y por último escalando.

**Cómo se ejecuta cada plan:** son planes TDD. El ciclo por tarea siempre es:
1. Escribir el test que falla.
2. Correr el test y ver que falla (por la razón correcta).
3. Escribir el código mínimo.
4. Correr el test y ver que pasa.
5. Correr TODA la suite (`cd apps/api && npm test`) y ver que sigue verde.
6. Commit.

## Convenciones del repo (leer una sola vez, aplica a todos los planes)

- **Monorepo npm workspaces.** Backend en `apps/api`, frontend en `apps/web`.
- **Backend:** Node + TypeScript (ESM, imports con extensión `.js`), Fastify, Drizzle ORM,
  Postgres. Validación con **zod** en cada ruta (`schema.safeParse(request.body)`).
- **Aislamiento multi-tenant:** TODA lectura/escritura de datos de taller pasa por
  `TenantDb` (`apps/api/src/db/scope.ts`), obtenido con `forTenant(tenantId)`. NUNCA
  escribas una query Drizzle cruda contra una tabla de datos: rompe el aislamiento y los
  tests de `isolation.test.ts` lo detectan. Excepción actual: rutas de plataforma
  (`admin.ts`) y billing, que filtran a mano — se corrige en el plan de seguridad.
- **Tests:** vitest sobre Postgres real. Patrón (ver `apps/api/test/orders.test.ts`):
  ```ts
  import { afterAll, beforeEach, describe, expect, it } from "vitest";
  import { pool } from "../src/db/client.js";
  import { createTenant } from "../src/db/admin.js";
  import { forTenant, type TenantDb } from "../src/db/scope.js";
  import { resetDb } from "./helpers.js";

  let tdb: TenantDb;
  const actor = { userId: null, userName: "Test" };
  beforeEach(async () => { await resetDb(); const t = await createTenant({ name: "A", slug: "a" }); tdb = forTenant(t.id); });
  afterAll(async () => { await pool.end(); });
  ```
  `resetDb()` trunca todas las tablas. Necesita Postgres corriendo (Docker:
  `npm run db:up` desde la raíz; ver memoria "Local DB fallback": puerto host 5433).
- **Correr los tests:** `cd apps/api && npm test` (toda la suite) o
  `npm test -- orders` (un archivo). Typecheck: `npm run typecheck`.
- **Migraciones Drizzle:** editás `apps/api/src/db/schema.ts`, después
  `cd apps/api && npm run db:generate` (crea SQL en `apps/api/drizzle/`), después
  `npm run db:migrate` (aplica). NUNCA edites a mano los `.sql` generados salvo que el
  plan lo diga explícitamente (backfills).
- **Dinero:** HOY está en `doublePrecision` (float). El plan 02 lo migra a **enteros en
  centavos**. Hasta que ese plan esté hecho, cualquier código nuevo que toque plata debe
  seguir usando `number` pero está sujeto a esa migración.
- **Commits:** frecuentes, uno por tarea. Mensaje en imperativo, español o inglés (seguí
  el estilo del historial). Terminá el mensaje con:
  ```
  Co-Authored-By: Claude Fable 5 <noreply@anthropic.com>
  ```

## Inventario completo de tareas (trazabilidad con la auditoría)

Cada ítem de la auditoría tiene un ID acá y un plan destino. Si algo no está, es un bug
del plan: avisá.

### Fase 0 — Quick Wins → plan 01
- QW-1: Constraint `quantity >= 0` en productos + guard en código.
- QW-2: `ConfirmDialog` antes de "Finalizar y entregar" con resumen (frontend).
- QW-3: Sanitizar `tallerNombre` y nombres antes del prompt del bot.
- QW-4: Cap de input del bot (1000 chars) + borrar endpoint `/api/transactions/vehicle`.
- QW-5: Guard: no editar órdenes finalizadas.
- QW-6: Timezone UTC-3 en reportes/calendario/usage.
- QW-7: Rate limit global + endpoints caros.
- QW-8: Sanitizar CSV export (fórmula injection).

### Fase 1 — Dinero y transacciones → plan 02
- MT-1: Helper `withTenantTx` (transacción Drizzle que respeta `TenantDb`).
- MT-2: `finalizeOrder` atómico (stock + ingreso + orden + vehículo en una transacción).
- MT-3: `reopenOrder` atómico.
- MT-4: Migrar todas las columnas de dinero a enteros en centavos (expand → backfill → contract).
- MT-5: Formateo de dinero en el frontend en centavos.

### Fase 2 — Seguridad → plan 03
- SEC-1: Rate limit por endpoint caro (reportes, uploads, media, bot).
- SEC-2: Política de contraseñas (mínimo) + lockout por usuario.
- SEC-3: Backups off-site (R2/S3) + restore probado + confirmar cron.
- SEC-4: Tests de aislamiento cross-tenant de billing.
- SEC-5: Validación de magic bytes en uploads.
- SEC-6: Mensajes de error genéricos al cliente (no filtrar interno).
- SEC-7: Rotación/segregación del token de WhatsApp (documentar + runbook).
- SEC-8: Confirmar esquema HMAC de Mobbex en sandbox.
- SEC-9: Headers de seguridad globales (verificar Caddy) + redacción de webhook bodies.

### Fase 2 — Bot / IA → plan 04
- BOT-1: Sanitizar interpolaciones en el system prompt.
- BOT-2: Cap de input + rate limit por número (10 msg/min).
- BOT-3: Confirmación antes de escrituras destructivas (`registrar_ingreso`, `crear_presupuesto`).
- BOT-4: Validación de formato de patente.
- BOT-5: Cuota por tokens (no por mensajes) + contar turnos.
- BOT-6: Fallback de modelo + timestamp anti-replay en webhook.

### Fase 3 — Lógica de negocio → plan 05
- BL-1: Link `workOrderId` en la tabla `transactions` + reversa de ingreso correcta.
- BL-2: Revertir ingreso al borrar vehículo.
- BL-3: Sync inverso orden→vehículo.
- BL-4: Guard de sesiones de timer solapadas.
- BL-5: Manejo de error de stock en entrega (no dejar "Entregado" sin finalizar).
- BL-6: Redefinir métricas (retención, "predicción" → "promedio").
- BL-7: Guard de stock negativo en ajuste manual concurrente.

### Fase 4 — Cobro y facturación → plan 06
- PAY-1: Modelo de pagos + pagos parciales + cuenta corriente (deuda).
- PAY-2: IVA y descuentos en presupuestos y ventas.

## Definición de "hecho" (aplica a toda tarea de código)

Una tarea está hecha solo si:
1. Su test nuevo pasa.
2. `cd apps/api && npm test` pasa entero (0 fallos).
3. `cd apps/api && npm run typecheck` pasa (0 errores).
4. Para cambios de frontend: `cd apps/web && npm run build` compila, y se verificó en el
   navegador con las herramientas de preview (screenshot/console sin errores).
5. Está commiteado.

Si algo no cumple, la tarea sigue `in_progress`. No se tilda por optimismo.
